Documents & e-sign

The console Documents section is an encrypted workspace library in git — separate from ticket-only attachments. Use it for templates, field layouts, and retained signed copies.

Library & folders

  • Upload PDFs (and other files) into the site’s Documents store.
  • Create folders / subfolders; drag files between folders.
  • Move, copy, duplicate, rename, and delete via the file menu.

Stored under your data repo as:

crm-data/{site}/documents/
  manifest.json.enc
  {document-id}.enc

PDF fields & share links

  • Place fields — signature, initials, name, date, number, text, checkbox, dropdown, and white-out regions. Number fields enforce numeric input in the preview and public signer.
  • Edit existing content — Shift-peek selectable PDF text and unmapped AcroForm controls; convert text while preserving its box and available styling. White-out can structurally scrub underlying text/widgets.
  • Prepare the layout — duplicate and reorder overlapping fields, resize with collision stops, tune text size, line spacing and alignment, and choose border-only or labeled stamps.
  • Create share link — a Worker e-sign session for a contact + ticket. The signer opens the link and completes required fields. Revoke a pending link from its creation dialog or ticket activity.
  • When signing finishes, the signed PDF attaches to the ticket (with audit note / hashes) — not automatically into Documents.
  • Download rebuilds writable CRM controls as fillable AcroForm widgets. Signature and initials become standard /FT /Sig fields; PDF has no separate initials or number field type, so initials use a named signature field and numbers use a text field with the CRM numeric constraint.
  • Overwrite source replaces the library PDF with the baked fillable copy after confirmation. Locked values and white-outs become permanent; writable controls remain fillable.

What a completed signature contains

  1. Visual e-sign ink. Drawn or typed signature and initials are fitted into their prepared fields; the remaining form values are baked into the completed PDF.
  2. Per-site PKCS#7 seal. Your Worker adds a standard PDF digital signature using an RSA-2048 certificate generated once for that CRM site. Acrobat and compatible viewers can detect byte changes after signing.
  3. Trusted completion time. After sealing, the Worker appends a DigiCert RFC 3161 document timestamp. Only the PDF hash is sent to the timestamp authority; the document itself stays in your workflow.
  4. Ticket audit. The activity note records unsigned and final SHA-256 hashes, session, signer metadata, site-certificate fingerprint, timestamp details, and verification URLs.

Trust boundary: the DigiCert timestamp is independently trusted and proves when the final document existed. The signer identity certificate is self-signed, so Acrobat may report that the identity is not globally trusted until the site certificate is imported. This is not a public-CA, AATL/EUTL, or qualified electronic signature (QES).

Certificate and verification endpoints

Every site exposes its public certificate and a verifier through its Worker: 

GET  /v1/{site}/sign/cert
POST /v1/{site}/sign/verify

{
  "pdfBase64": "..."
}

Verification checks the site seal against that site’s public certificate and validates every embedded RFC 3161 timestamp against the bytes it covers. New completed PDFs should report fullyVerified: true. Older signed copies without a trusted timestamp can still pass the site-seal check.

Failure behavior

The public timestamp service is an external dependency. If it is temporarily unavailable, completion keeps the valid site seal and records the timestamp failure instead of losing the signer’s work. If cryptographic sealing itself fails, the visual signed PDF and ticket workflow still complete with that limitation recorded in the API response.

Tickets ↔ Documents

  • Ticket files stay on the ticket until you choose ⋮ → Save to Documents (name + folder). Signed copies can retain contact + e-sign audit on the library record.
  • Contact detail shows a Signed documents list (deduped across ticket + library). Open ticket and/or Open in Documents when each still exists.
  • Deleting a ticket that still has a signed PDF not saved to Documents prompts an extra warning first.

Worker vs browser

Library CRUD is browser → GitHub (like contacts/tickets). Creating and completing e-sign sessions, cryptographic sealing, timestamping, and verification go through your CRM Worker (/sign/sessions and /sign/*).
